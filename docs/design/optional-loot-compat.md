# Optional addon block loot

The Act V 110-mod server log reports 85 `Unknown registry key ... minecraft:item` loot-table errors. Each named table exists in its pinned addon JAR, and each has exactly one `minecraft:item` entry pointing to the missing item of the same name. The source list is `compatibilityPending.missingItemLootTables` in [Act V evidence](../verification/act-five-runtime.json); its sorted IDs have SHA-256 `397e3d1bdc589d4e639efa9624dc07851f458743b0e573ece03d178e79a62a64` (newline-separated). This is a resource/registration mismatch, not evidence that the blocks themselves are loaded.

Bytecode class names above and the exact JSON paths are from those local pinned JARs. The Mekanism factory tables include `copy_name` and `copy_components` for owner, security, upgrades, energy, inventory and chemicals. Copying or replacing those tables with simplified drops would lose machine contents or metadata.

`pack/kubejs/server_scripts/entrelumen_optional_loot_compat.js` checks the 85 exact item IDs during KubeJS `generateData('after_mods')`. For a missing item, it emits a higher-priority JSON at the same `namespace:loot_table/blocks/<name>.json` resource path with `neoforge:item_exists` on that item. The failed condition gives an empty table before the missing item reaches the loot codec. For an existing item it emits nothing, so the full original JAR table remains selected. No JAR content, drops, items or inventories are copied or changed. [NeoForge 1.21.1 data-load conditions](https://docs.neoforged.net/docs/1.21.1/resources/server/conditions/) explicitly specify early evaluation and empty-table replacement for failed loot conditions.

`/reload` reevaluates the same registered item set and regenerates the appropriate resource selection. Installing or removing an addon that changes item registration requires a restart; the next load then selects the newly applicable branch. The `[ENTRELUMEN_OPTIONAL_LOOT]` line reports the number of empty fallbacks by namespace; it is a generation receipt, not proof that all original tables decoded or that drops were correct. The root integration QA must confirm the final loaded tables and representative machine drops in Minecraft, including after `/reload`.

`python -m unittest tools.test_optional_loot_compat` runs the JS against absent, present and mixed registry mocks, fixes the exact observed 85-ID set, and checks the condition/resource path. When local pinned JARs are available it also verifies hashes, source paths and entry item IDs. CI without `catalog/local-paths.json` explicitly skips only that optional JAR check; the JS behavior checks still run.

## Integration result

[Runtime evidence](../verification/optional-loot-runtime.json) now verifies the installed guard in the 110-dependency server. Two passing receipts separated by `/reload` cover all 380 native block-loot resources: 295 tables retain their complete normalized native contents, and the 85 absent-item tables resolve to empty loot. NeoForge excludes the failed conditional entries from the loaded registry; `ReloadableServerRegistries.Holder.getLootTable` supplies `LootTable.EMPTY` for those lookups. The initial QA helper was corrected to test this actual lookup behavior instead of requiring a registered empty entry.

Six representative blocks each produced their correct single item. Four Mekanism factories also retained a custom name and 12,345 stored energy. The temporary test used in-memory block entities and was removed afterwards. Its Rhino reflection caused a client-sound-field inspection error on the dedicated server; a separate final startup with only shipped scripts had zero ERROR lines and no loot parse failures. Both owned server runs stopped cleanly. The matching guard is installed in the client, which was not launched for this server-data change. These checks do not establish manual mining, every populated inventory component or performance acceptance.
