# RFTools and XNet — finite workshop infrastructure

This batch adds five distinct content mods and one required library for Minecraft 1.21.1 / NeoForge 21.1.249. The six official CurseForge files are already present in the read-only ATM10 8.1 reference instance at `E:/curseforge/Instances/All the Mods 10 - ATM10/mods`. Their actual lengths and SHA-1 match that instance's installed CurseForge file metadata; `catalog/curated.json` pins SHA-256 and project/file IDs. Only licensed JAR references and metadata were used. No ATM10 scripts, quests, assets or story were copied, and no JAR is committed here.

Every JAR declares an MIT License link and has no embedded JarJar provider. CurseForge marks each file Client + Server, 1.21.1, NeoForge, with `allowModDistribution=true`. The JAR manifests require McJtyLib **at least 1.21-9.0.21** and Base **at least 1.21-6.0.11** for Builder, Utility, Power and XNet; Base itself requires McJtyLib. Installed CurseForge relationships name the same required projects. This six-file closure adds 4,845,367 compressed bytes. The metadata supports curation, not a launch or performance claim.

AE2 remains the sole principal digital item store. RFTools Storage and RFTools Dimensions are intentionally absent. The latter would add another dimension stack; the former would duplicate AE2. RFTools Power cells store FE. JAMD remains the mining dimension. Builder's quarry is a powered project tool there, not an authority check: a gifted machine/card still works elsewhere. The first normal build requires the Act III `handling_core`; the base quarry card additionally takes two ironwood ingots (Act IV), the material every non-keystone quarry of the pack takes since the recipe audit of 25 September 2026 ([progression-functions](progression-functions.md), [recipe-design-rules](recipe-design-rules.md#materiales-de-acto)). Build an observatory shell with supplied blocks, then use a measured JAMD quarry for stone/ore batches rather than making a second resource dimension.

XNet has a distinct reason to stay beside AE2, Pipez, LaserIO and Integrated Dynamics: one controller can use configurable item, fluid, FE and logic channels, while routers connect named local channels. McJty's [XNet documentation](https://mcjty.eu/docs/mods/xnet) describes the controller/connector network, eight local channels, power draw and router arrangement. The normal controller takes Mekanism's reinforced alloy (the Act III material) in place of the gold ingot at its foot; routers and wireless routers keep their native recipes, because they only work under a controller, and cables and connectors remain cheap infrastructure. A useful Act III project is an FE-level sensor that feeds fuel only when the generator buffer is low, and routes output to the next workshop. This is a proposal for original projects, not a shipped quest.

RFTools Utility's native [feature list](https://www.curseforge.com/minecraft/mc-mods/rftools-utility) includes screens, crafters, spawning and teleportation. The matter receiver takes the reinforced alloy on top; the charged porter only reaches receivers and the transmitter needs a destination, so both stay native. The environmental controller takes the alloy in place of an ender pearl before its optional, powered modules become available. The spawner is a mob farm, an Act IV function ([progression-functions](progression-functions.md)), and takes an ironwood ingot before any native mob recipe. Of the JAR's 70 vanilla-mob spawner data recipes, 69 remain intact and demand their listed matter and FE. `minecraft_wither.json` asked 0.1 Nether star of matter and 20,000 FE for a Wither that drops a whole star, a star loop; the `boss_drops` family of `tools/generate_family_balance.py` removes it ([mod-pingpong](mod-pingpong.md#botines-de-jefe)). `minecraft_ender_dragon.json` (end stone and 100,000 FE) stays: a spawned dragon has no End fight, so it drops no dragon heart or egg. Real throughput and material economics still need in-game measurement before accepting a farm plan. No item provenance, team, act or gift checks were added.

RFTools Power retains the coal generator as a finite early fuel route, with native stronger generators and local energy cells. The simple and regular dimensional cells each take the reinforced alloy (one in place of a diamond, two in place of the lower redstone blocks); the advanced cell already depends on the regular cell. They distribute stored FE, not item inventory and not a new world. The JAR also registers `rftoolspower:dimensionalcell_creative`, but none of its 19 recipe JSONs produces it. No authored content/reward references it. Do not place it in rewards or survival loot. Power and teleport throughput are still runtime questions.

## Native recipe audit and static adjustment

The pinned Base has 12 recipe JSONs; Builder 42, Utility 137, Power 19 and XNet 37. `tools/generate_rftools_balance.py` reads and hashes the locked JARs, scans all 235 recipes in the four functional mods, and changes only these 8 native IDs (its `CHANGES` table, since the recipe audit of 25 September 2026). Only the builder, a milestone, takes a component; the other gates take their act's material, one slot on the drawing's axis or a mirrored pair:

| Native ID | Takes | In place of | Act | Purpose |
| --- | --- | --- | --- | --- |
| `rftoolsbuilder:builder` | `handling_core` | the bottom redstone | III | Construction machine |
| `rftoolsbuilder:shape_card_quarry` | 2 ironwood ingots | the top corner redstone | IV | Quarries are an Act IV function |
| `rftoolsutility:spawner` | ironwood ingot | the bottom-left redstone | IV | Mob farms are an Act IV function |
| `rftoolsutility:matter_receiver` | reinforced alloy | the middle top iron ingot | III | Teleport destination |
| `rftoolsutility:environmental_controller` | reinforced alloy | the bottom-right ender pearl | III | Charged environmental modules |
| `rftoolspower:dimensionalcell_simple` | reinforced alloy | the bottom diamond | III | Wireless energy |
| `rftoolspower:dimensionalcell` | 2 reinforced alloys | the bottom corner redstone blocks | III | Wireless energy |
| `xnet:controller` | reinforced alloy | the bottom gold ingot | III | Logic and cross-workshop routing |

The charged porter and XNet's routers and wireless routers keep their native recipes: the porter only reaches receivers and routers only work under a controller. Each modification replaces one repeated commodity or a single slot on the drawing's axis. The generator reverses each edit and compares the complete original JSON to protect the serializer, native category, result, conditions, remainder fields and all untouched ingredients. In particular, `shape_card_quarry` stays `mcjtylib:copy_components`, so configured card data is retained. The six quarry output variants descend from its base card; the alternative dirt-cycle recipe cannot craft one without a card. Other changed outputs each have one native acquisition route. Native syringe, spawner-mob and cell-upgrade serializers are untouched. KubeJS replaces only present native recipe IDs and reports its loaded-output check; it cannot prove crafting contents or machine behavior before a real server run.

The component graph the generator reports (`handling_core`, `power_regulator`, `energy_coupler`) has no RFTools/XNet input and no cycle. `handling_core` needs Create precision assembly, Modular Routers modules and `power_regulator`; `power_regulator` needs Mekanism's basic circuit, IE steel plates and `energy_coupler`. Those independent acquisition paths are documented in [Act III recipes](act-three-recipes.md). The reinforced alloy comes from Mekanism's metallurgic infuser and ironwood from the Twilight Forest, neither through RFTools. The basic RFTools coal generator remains ungated, so using its FE for the first Mekanism circuit does not create a power bootstrap cycle.

## Fullpack QA contract

`RFToolsRecipeGameTests` lives only in the `fullpackGameTest` source set. On a server with the real six JARs and generated KubeJS script, its first test queries the live `RecipeManager` for the 8 staged IDs and the 3 kept native (charged porter, router, wireless router). It checks each loaded serializer, result ID and count, full 3×3 match with the real integration item, rejection of the former grid, and empty crafting remainders. Its second test configures a native `ShapeCardItem` through the RFTools Builder API, crafts a quarry card from that configured input, and compares the entire native `getComponentsToPreserve()` set plus dimension, offset and tag-matching values on the result. The native API is reached by reflection, so the QA source set adds no McJty compile dependency. These tests close the static recipe gap only after their live run; they make no claim about quarry throughput, power costs or client behavior.

No family JAR was rejected: all six satisfy the declared loader/dependency ranges and official file metadata. This does not establish runtime compatibility with the other 151 JARs. Integration must verify startup, actual JEI/EMI recipes and component-copy behavior, JAMD quarry cost/chunk loading and claims, XNet channels, teleport safety, spawner boss economics, client UI and frame-time/heap impact in owned client/server profiles. These runtime results require separate QA evidence.

Integration update, 23 September (with that date's components; this record does not cover the audited recipes of 25 September): both recipe GameTests passed with the real mods, including all 11 ingredient/result/remainder checks and the configured card's complete native shape-data component. The normal 122-dependency dedicated server started, loaded the 11 adjusted outputs, saved and exited with no ERROR lines. Both stopped clients received the six dependencies and script, retaining the previous production companion JAR. Their launch, rendered recipes, machine workloads and performance remain pending; no Computer Use was performed. See the [bounded runtime receipt](../verification/rftools-resource-runtime.json).
