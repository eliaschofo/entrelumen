# RFTools and XNet — finite workshop infrastructure

This batch adds five distinct content mods and one required library for Minecraft 1.21.1 / NeoForge 21.1.249. The six official CurseForge files are already present in the read-only ATM10 8.1 reference instance at `E:/curseforge/Instances/All the Mods 10 - ATM10/mods`. Their actual lengths and SHA-1 match that instance's installed CurseForge file metadata; `catalog/curated.json` pins SHA-256 and project/file IDs. Only licensed JAR references and metadata were used. No ATM10 scripts, quests, assets or story were copied, and no JAR is committed here.

| --- | --- | --- |
| [McJtyLib 1.21-9.0.21](https://www.curseforge.com/minecraft/mc-mods/mcjtylib/files/8256201) | 233105 / 8256201 | Shared library and native component-copy serializer |
| [RFTools Base 1.21-6.0.11](https://www.curseforge.com/minecraft/mc-mods/rftools-base/files/8256204) | 326041 / 8256204 | Frames, manual and common instruments |

| [RFTools Utility 1.21-7.0.12](https://www.curseforge.com/minecraft/mc-mods/rftools-utility/files/8256212) | 342466 / 8256212 | Crafter, logic, displays, teleportation and material-fed spawner |
| [RFTools Power 1.21-7.0.6](https://www.curseforge.com/minecraft/mc-mods/rftools-power/files/8256213) | 290209 / 8256213 | Fuelled generation, finite energy cells and wireless distribution |

Every JAR declares an MIT License link and has no embedded JarJar provider. CurseForge marks each file Client + Server, 1.21.1, NeoForge, with `allowModDistribution=true`. The JAR manifests require McJtyLib **at least 1.21-9.0.21** and Base **at least 1.21-6.0.11** for Builder, Utility, Power and XNet; Base itself requires McJtyLib. Installed CurseForge relationships name the same required projects. This six-file closure adds 4,845,367 compressed bytes. The metadata supports curation, not a launch or performance claim.

AE2 remains the sole principal digital item store. RFTools Storage and RFTools Dimensions are intentionally absent. The latter would add another dimension stack; the former would duplicate AE2. RFTools Power cells store FE. JAMD remains the mining dimension. Builder's quarry is a powered project tool there, not an authority check: a gifted machine/card still works elsewhere. The first normal build requires the Act III `handling_core`; the base quarry card additionally consumes a `spectral_lens` (Act IV) since 24 September 2026, like every other quarry of the pack ([progression-functions](progression-functions.md)). Build an observatory shell with supplied blocks, then use a measured JAMD quarry for stone/ore batches rather than making a second resource dimension.

XNet has a distinct reason to stay beside AE2, Pipez, LaserIO and Integrated Dynamics: one controller can use configurable item, fluid, FE and logic channels, while routers connect named local channels. McJty's [XNet documentation](https://mcjty.eu/docs/mods/xnet) describes the controller/connector network, eight local channels, power draw and router arrangement. The normal controller, router and wireless router recipes each consume an existing `routing_matrix`; cables and connectors remain cheap infrastructure. A useful Act III project is an FE-level sensor that feeds fuel only when the generator buffer is low, and routes output to the next workshop. This is a proposal for original projects, not a shipped quest.

RFTools Utility's native [feature list](https://www.curseforge.com/minecraft/mc-mods/rftools-utility) includes screens, crafters, spawning and teleportation. The normal receiver and charged porter each acquire a `routing_matrix`; the transmitter remains native because it needs a destination. The environmental controller uses a `power_regulator` before its optional, powered modules become available. The spawner uses an `ecosystem_capsule` before any native mob recipe; the JAR's 70 vanilla-mob spawner data recipes remain intact and continue to demand their listed matter and FE. For example, its pinned `data/rftoolsutility/recipe/minecraft_wither.json` lists a nether-star matter input and 20,000 FE, while `minecraft_ender_dragon.json` lists end stone and 100,000 FE. Real throughput, boss drops and material economics need in-game measurement before accepting a farm plan. No item provenance, team, act or gift checks were added.

RFTools Power retains the coal generator as a finite early fuel route, with native stronger generators and local energy cells. The simple and regular dimensional cells each consume a `power_regulator`; the advanced cell already depends on the regular cell. They distribute stored FE, not item inventory and not a new world. The JAR also registers `rftoolspower:dimensionalcell_creative`, but none of its 19 recipe JSONs produces it. No authored content/reward references it. Do not place it in rewards or survival loot. Power and teleport throughput are still runtime questions.

## Native recipe audit and static adjustment

The pinned Base has 12 recipe JSONs; Builder 42, Utility 137, Power 19 and XNet 37. `tools/generate_rftools_balance.py` reads and hashes the locked JARs, scans all 235 recipes in the four functional mods, and changes only these 11 native IDs:

| Native ID | Existing component | Purpose |
| --- | --- | --- |
| `rftoolsbuilder:builder` | `handling_core` | Act III construction machine |
| `rftoolsbuilder:shape_card_quarry` | `spectral_lens` | Quarries are a spectral lens function (Act IV) since 24 September 2026 |
| `rftoolsutility:spawner` | `ecosystem_capsule` | Stage material-fed ecology service |
| `rftoolsutility:matter_receiver`, `charged_porter` | `routing_matrix` | Powered destination and portable travel |
| `rftoolsutility:environmental_controller` | `power_regulator` | Charged environmental modules |
| `rftoolspower:dimensionalcell_simple`, `dimensionalcell` | `power_regulator` | Wireless energy infrastructure |
| `xnet:controller`, `router`, `wireless_router` | `routing_matrix` | Logic and cross-workshop routing |

Each modification replaces one repeated commodity or fills an empty crafting slot. The generator reverses each edit and compares the complete original JSON to protect the serializer, native category, result, conditions, remainder fields and all untouched ingredients. In particular, `shape_card_quarry` stays `mcjtylib:copy_components`, so configured card data is retained. The six quarry output variants descend from its base card; the alternative dirt-cycle recipe cannot craft one without a card. Other changed outputs each have one native acquisition route. Native syringe, spawner-mob and cell-upgrade serializers are untouched. KubeJS replaces only present native recipe IDs and reports its loaded-output check; it cannot prove crafting contents or machine behavior before a real server run.

The existing component graph has no RFTools/XNet input and no component cycle. `handling_core` needs Create precision assembly, Modular Routers modules and `power_regulator`; `routing_matrix` needs AE2 processors, a PneumaticCraft PCB, AA palis and `calibration_frame`; `power_regulator` needs Mekanism's basic circuit, IE steel plates and `energy_coupler`. Those independent acquisition paths are documented in [Act III recipes](act-three-recipes.md). `ecosystem_capsule` uses Bumblezone pollen, Productive Bees wax and `living_matrix`; wax has a basic centrifuge route independent of the RFTools spawner. The basic RFTools coal generator remains ungated, so using its FE for the first Mekanism circuit does not create a power bootstrap cycle.

## Fullpack QA contract

`RFToolsRecipeGameTests` lives only in the `fullpackGameTest` source set. On a server with the real six JARs and generated KubeJS script, its first test queries the live `RecipeManager` for all 11 IDs. It checks each loaded serializer, result ID and count, full 3×3 match with the real integration item, rejection of the former grid, and empty crafting remainders. Its second test configures a native `ShapeCardItem` through the RFTools Builder API, crafts a quarry card from that configured input, and compares the entire native `getComponentsToPreserve()` set plus dimension, offset and tag-matching values on the result. The native API is reached by reflection, so the QA source set adds no McJty compile dependency. These tests close the static recipe gap only after their live run; they make no claim about quarry throughput, power costs or client behavior.

No family JAR was rejected: all six satisfy the declared loader/dependency ranges and official file metadata. This does not establish runtime compatibility with the other 151 JARs. Integration must verify startup, actual JEI/EMI recipes and component-copy behavior, JAMD quarry cost/chunk loading and claims, XNet channels, teleport safety, spawner boss economics, client UI and frame-time/heap impact in owned client/server profiles. These runtime results require separate QA evidence.

Integration update, 23 September: both recipe GameTests passed with the real mods, including all 11 ingredient/result/remainder checks and the configured card's complete native shape-data component. The normal 122-dependency dedicated server started, loaded the 11 adjusted outputs, saved and exited with no ERROR lines. Both stopped clients received the six dependencies and script, retaining the previous production companion JAR. Their launch, rendered recipes, machine workloads and performance remain pending; no Computer Use was performed. See the [bounded runtime receipt](../verification/rftools-resource-runtime.json).
